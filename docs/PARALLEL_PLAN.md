# 병렬 개발 실행 계획

2026-10-12 / 첫 병렬 실행 완료 및 통합 검증 진행. 결과와 잔여 범위는 STATUS.md에 기록한다.

## 1. 운영 방식

공통 계약을 먼저 확정한 뒤 인증, 게시판, 학생 참여·QR을 병렬로 개발한다. 통합 담당은 실시간·파일·운영·검증을 맡으며 공통 파일 변경을 관리한다. 동시에 네 작업 슬롯이 가능하다면 통합 담당 1명과 기능 담당 3명으로 구성한다. 담당 D는 통합 담당과 동일한 역할이다.

## 2. 작업 분담

|담당|소유 범위|첫 결과물|완료 증거|
|---|---|---|---|
|A 인증·권한|auth, policy, security tests|Google·익명 세션, 교사 자격·역할, 공통 authorize|외부 도메인·위조·타인 접근·정지 계정 차단 테스트|
|B 게시판·작성|boards UI/server|교사 홈, 세 가지 배치, 게시·댓글·승인|생성→작성→승인→닫기 흐름 및 저장 검증|
|C 학생 참여·QR|join, share UI/server|로그인/익명 선택, 목적지별 QR·코드, 회수|실기기 QR 진입·복귀 및 범위·만료 테스트|
|D 통합·기반·검증|app routes, contracts, ui, db, media, realtime, admin, E2E, CI|프로젝트 뼈대·공통 계약·파일·이벤트 연결|통합 E2E·부하·백업 복원·출시 체크|

각 담당은 자신의 UI·서버 기능을 함께 맡는다. A가 공통 권한 검사를 제공하기 전에는 D가 정의한 인터페이스와 모의 구현으로 진행한다. 모의 구현은 테스트 전용이며 실제 서버 통합 전 권한 검사를 생략한 API를 배포하지 않는다.

## 3. 단계와 의존성

|단계|작업|병렬 가능 여부|통과 조건|
|---|---|---|---|
|G0 계약 동결|D 주관, A/B/C 검토: 역할·페이지·DTO·스키마·디자인 토큰·fixture·명령 확정|공동 검토 후 단일 반영|같은 입력·출력·오류·담당 파일 합의|
|G1 독립 구현|A 인증/정책, B 게시판/작성, C 참여/QR, D 업로드/실시간 기반|4개 레인 동시|각 레인 계약·기능 테스트 통과|
|G2 첫 통합|A 정책을 B/C/D에 연결, 실제 DB·OAuth·이벤트·파일 통합|기능별 병렬 수정, 마이그레이션 순차|교사 생성→QR→두 참여 방식→작성→교사 승인 성공|
|G3 수업 완성|B 배치·댓글·닫기, C 글/섹션/제출 QR, A 차단·세션 연결, D 내보내기·관리·복구|4개 레인 동시|PRD P0 항목 완료 및 권한 회수 검증|
|G4 출시 검증|E2E·모바일·500세션 목표 부하·백업 복원·운영 설정|테스트 실행은 병렬, 출시 판정은 단일|결함 해결·실제 학교 계정 및 QR 확인|
|G5 확장|P1 고급 게시판 → P2 화이트보드 → P3 게임·AI|각 단계 계약 재정의 후 분업|단계별 별도 수용 기준 충족|

주요 임계 경로는 `G0 → 인증·공유 권한 → 실제 DB 통합 → 파일·실시간 권한 회수 → 출시 검증`이다. 화면 개발은 G1부터 병렬 진행하지만 출시 판단은 이 경로를 단축해서 생략하지 않는다. D의 기반 작업이 병목이 되면 G2 종료 후 여유가 생긴 담당에게 명시적으로 모듈 소유권을 넘긴다.

일정은 구현 담당 인원·학교 계정·배포 환경을 확인하고 G0 작업량을 산정한 뒤 확정한다. 병렬 작업 수만큼 전체 기간이 줄어든다고 가정하지 않는다.

## 5. 충돌 방지 규칙

1. 각 레인은 소유 디렉터리만 변경한다. 라우트 연결, package.json·잠금 파일, DB 스키마·마이그레이션, 공통 계약은 D만 반영한다.
2. 기능 담당은 필요한 계약 변경을 필드·이유·호환성·호출자 영향과 함께 제안한다. D가 계약과 fixture를 갱신한 뒤 각 레인이 따라간다.
3. Git 초기화 이후 `feat/auth-policy`, `feat/boards`, `feat/join-share`, `chore/integration`처럼 브랜치·worktree를 분리한다. 공유 작업 디렉터리에서 동시 checkout을 하지 않는다.
4. 마이그레이션 번호와 적용 순서는 D가 관리한다. 서로 다른 레인이 임의로 같은 테이블을 재정의하지 않는다.
5. 큰 기능 전체를 기다리지 않고 계약 단위 작은 PR을 만든다. 통합 순서는 공통 계약 → 정책 → 게시판/공유 → 미디어/실시간 → 전체 흐름이다.
6. 매 인계에 변경 파일·API·테스트 결과·제약·다음 의존 작업을 기록한다. 역할·공개 범위·공유 회수 변경은 A와 D가 함께 검토한다.
7. 실패한 통합을 UI 임시 처리나 권한 검사 제거로 통과시키지 않는다. 원인 레인에서 수정하고 영향 테스트를 재실행한다.

## 6. 레인별 작업 요청 템플릿

“PRD와 IMPLEMENTATION 및 AGENTS를 읽고 [작업 ID]를 구현한다. 소유 디렉터리는 [경로]다. 공통 계약을 변경해야 하면 먼저 통합 담당에게 변경안을 보낸다. 작업 완료 시 기능·권한 검사·오류 처리·관련 테스트 결과를 보고한다. 실제 비밀값이나 학교 데이터를 fixture로 사용하지 않는다.”

P1부터는 작업을 고급 배치/미디어, 투표/모둠, 공유/내보내기, 통합/검증으로 다시 배분한다. P2는 캔버스 모델과 동시 편집 충돌 정책을 먼저 합의하고 도구·동기화·수업 제어·출력으로 나눈다. P3는 게임·AI·외부 연동·운영으로 나눈다. 후속 단계의 팀 분배는 P0 파일 경계를 기계적으로 유지하지 않고 실제 의존성을 재검토한다.
